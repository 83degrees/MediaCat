# DDR-03-003 — Resolve Artwork Sources at Catalogue Load

## Status

Proposed

## Decision

MediaCat schema v4 stores artwork as an explicit source reference and resolves
that source once during catalogue load into the existing runtime artwork shape.

Schema v4 supports exactly two artwork source types:

- `ha-assets` — an item stores one relative path and resolves it against
  catalogue-level local and/or external bases;
- `direct` — an item stores its local and/or external route directly.

The normalized runtime item representation contains only:

```yaml
artwork:
  local: ...
  external: ...
```

where either route may be absent. Authoring fields such as `source_type` and
`path` do not cross the runtime consumer boundary.

MediaCat validates source configuration and path structure but does not probe
the local filesystem or public URL for asset existence or liveness.

## Context

The shared `83degrees/ha-assets` repository now provides the same media artwork
through two deliberately different delivery routes:

- Home Assistant local static serving under `/local/ha-assets/`;
- public unauthenticated HTTPS through GitHub Pages.

Storing both fully expanded routes independently on every catalogue item would
duplicate shared base configuration and make route changes a per-item migration.
Conversely, exposing source-specific authoring details to consumers would make
the stored catalogue schema leak into runtime contracts.

MediaCat already owns catalogue loading and normalized item data, while route
selection for a playback endpoint remains outside MediaCat.

## Alternatives considered

1. Store full local and external URLs on every item as schema v3 did.
2. Store a generic asset object and defer all source resolution to consumers.
3. Store an explicit artwork source reference and resolve it at catalogue load.
   This is the selected option.
4. Probe local/public routes at catalogue load and choose whichever is live.

## Rationale

Load-time resolution keeps authoring concise while preserving the existing
consumer-facing artwork contract. A catalogue reload naturally rebuilds all
resolved routes after a source-base change, without making consumers understand
`ha-assets`, GitHub Pages, or repository paths.

Restricting v4 to `ha-assets` and `direct` keeps the schema closed and
purpose-specific. A future source type therefore requires explicit governed
schema evolution rather than becoming an accidental extension point.

Avoiding liveness probes keeps catalogue validation deterministic and prevents
external network or filesystem availability from deciding whether the
catalogue can load.

## Consequences / trade-offs

- Schema v4 is a clean cutover; legacy v3 artwork blocks without
  `source_type` are invalid.
- Shared source-base changes require a catalogue reload before resolved routes
  change.
- Broken local or external artwork routes remain operational faults rather than
  schema-load faults.
- Media Browser prefers resolved local artwork, then external artwork, without
  probing either route.
- Google Cast or other endpoint-specific route preference remains a consumer
  responsibility outside MediaCat.
- The returned-record artwork shape remains `local` / `external`, so this
  decision does not by itself change the current consumer contract version.
