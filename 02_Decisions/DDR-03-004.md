# DDR-03-004 — Use an Immutable Multi-Catalogue Registry and MediaCat-Owned Admin Boundary

## Status

Proposed

## Decision

MediaCat discovers ordinary YAML catalogue documents from
`/config/mediacat/catalogues/` and activates them as one immutable in-memory
registry keyed by each document's in-file `catalogue_id`.

The filename does not define catalogue identity. Duplicate catalogue IDs across
files invalidate the complete registry candidate.

MediaCat exposes a small supported Home Assistant administration interface for:

- schema and feature capability discovery;
- side-effect-free validation of supplied catalogue YAML; and
- transactional reload of the complete directory-backed registry.

Reload constructs and validates the complete candidate before one registry
reference replacement. A failed reload retains the previously active registry.

The separate MediaCat Manager product owns editing workflow, filesystem writes,
atomic file replacement, local history and restore. It consumes MediaCat's
supported validation and reload boundary rather than duplicating schema logic.

## Context

MediaCat previously loaded one fixed file,
`/config/mediacat/catalogue.yaml`, into one catalogue snapshot. The accepted
MediaCat Manager design requires multiple locally owned catalogues, normal
administration without private-repository access, and safe activation without a
Home Assistant restart.

Item identity was already catalogue-scoped as `(catalogue_id, item_id)`, but the
runtime loader, resolver storage and Media Source adapter assumed one file and
one active catalogue. A manager that copied MediaCat validation rules would
create two schema authorities and would drift as the schema evolved.

## Alternatives considered

1. Retain one fixed catalogue file and make Manager edit only that file.
2. Derive catalogue identity from each filename.
3. Let Manager own validation and replace MediaCat's runtime data directly.
4. Load files independently and replace active catalogues one at a time.
5. Use an immutable MediaCat-owned registry keyed by in-file identity, with a
   supported validation/capability/reload boundary. This is the selected option.

## Rationale

In-file identity preserves the existing schema authority and allows storage
names to change without changing logical references. Validating the complete
directory catches cross-file duplicate identities before activation.

One immutable registry replacement gives lookup and Media Source readers a
simple transactional boundary: they see either the complete old state or the
complete new state. Serializing reloads prevents competing candidates from
interleaving.

Keeping validation in MediaCat preserves one schema implementation and lets a
manager discover supported versions instead of permanently hard-coding schema
v4. Keeping filesystem mutation in Manager maintains a clear product boundary
and allows its snapshot/history policy to evolve independently.

## Consequences / trade-offs

- One invalid catalogue prevents activation of every change in that reload
  candidate; this deliberately favours registry consistency over partial
  availability.
- A failed reload preserves runtime state but does not restore changed disk
  files. Manager must perform snapshots and filesystem rollback.
- Initial setup still fails when the directory is absent, empty or contains an
  invalid/duplicate catalogue because there is no previous registry to retain.
- Media Source paths require catalogue scope when more than one catalogue is
  active. The sole-`curated_media` legacy paths remain supported for continuity.
- The admin interface adds a separately versioned provider contract.
- Adding future stored schema versions requires governed schema work but need
  not change the admin interface shape.
